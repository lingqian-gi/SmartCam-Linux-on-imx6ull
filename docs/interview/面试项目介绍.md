## 2. 项目背景与目标

### 2.1 背景

嵌入式 Linux 的"相机"方向横跨驱动（V4L2/UVC）、图像处理、流媒体协议、GUI、系统集成等多个技术域，是展示嵌入式软件综合能力的典型载体。项目基于**野火 iMX6ULL Pro 开发板**构建：

| 硬件 | 规格 | 在项目中的角色 |
|------|------|--------------|
| SoC | i.MX6ULL，Cortex-A7 @ 792MHz，单核 | 计算平台（无 VPU，软件编码） |
| 内存 | 512MB DDR3（CMA 占用后可用 <200MB） | 全系统内存预算约束 |
| 屏幕 | 7 寸 800x480 电容触摸屏，framebuffer `/dev/fb0` | 本地交互界面 |
| 摄像头 | USB UVC 摄像头，支持 MJPEG / YUYV 双格式 | 视频源 |

### 2.2 目标

把一块低成本 ARM 开发板变成一个**功能完备的网络相机**，覆盖：

1. 本地触摸屏实时预览与交互（拍照、录像、参数调节、相册）
2. 多协议流媒体推流（浏览器可直接看 + VLC/ffplay 可播放）
3. 远程 TCP 控制（拍照/录像/参数设置/状态查询）
4. 完整的存储管理（JPEG 拍照 + AVI 录像 + 自动清理）
5. 以 systemd 服务形式开机自启、稳定运行

### 2.3 设计约束（面试关键）

- **无 VPU**：H.264 硬件编码不可用，视频编码必须走软件路径
- **单核 792MHz + <200MB 可用内存**：所有设计围绕"省 CPU、省内存"
- **无 X Server**：GUI 必须用 framebuffer 后端（linuxfb）
- **板载存储为 tmpfs**：`/data` 重启即失，必须提供持久化方案

【口头陈述】

> "这个项目始于一个很实际的工程约束：i.MX6ULL 没有视频处理单元，只有单核 792MHz 的 Cortex-A7 和 512MB 内存。所以整个系统的设计哲学就是**在资源极度受限的情况下，通过架构和算法把性能抠出来**——比如利用摄像头硬件直接输出 MJPEG 走零编码路径，比如用 NEON 做颜色转换的 SIMD 优化，比如控制推流运行时内存只有 8MB。这也是这个项目区别于普通课程设计的地方。"

### 3.2 线程模型

常驻线程 + 动态 HTTP 客户端线程，各司其职（**解码在 Qt 主线程 + 帧池零拷贝**，无独立解码线程——见 §3.5 与难点 §12.9）：

```
Qt 主线程            采集线程             处理线程            RTSP 线程          控制线程          MJPEG-accept 线程
=========           ==========          ==========        ==========        ==========       ==========
displayTimer(33ms)  V4L2 DQBUF→拷贝→QBUF 等待新帧(条件变量)   epoll_wait 阻塞     epoll_wait 阻塞   accept() 新连接
  │                    │                  │                 │                 │                 │
  │-> lock(g_state)    │-> 通知处理线程    │-> YUYV→JPEG 编码 │-> RTP 分片       │-> TCP 命令分发   └─> 每 HTTP 客户端
  │-> 借rgb池槽         │-> 拍照/录像写入   │-> HTTP: update  │                  │-> 心跳超时检查       一个 handler
  │-> 解码/转换入槽      │-> unlock(g_state)│-> RTSP: feed    │                  │                     线程(detach)
  │-> publish→share     │                  │-> 磁盘写入       │                  │
  │-> setFrameShared    │                  │                 │                  │
  │-> requestRefresh    │                  │                 │                  │
  │-> QImage浅引用→QLabel│                  │                 │                  │
```

- **Qt 主线程**：GUI + 33ms 定时刷新预览画面；**显示解码也在主线程**（借帧池槽 → 解码入槽 → publish → share → 浅引用上屏），**完全单驱动**——`requestRefresh()` 是唯一上屏入口（真实模式由 displayTimer 发布后立即调用，Mock 模式由 main 的 Mock 定时器调用，无双定时器相位问题）
- **采集线程**：`DQBUF → 拷贝 → QBUF`，轻量快速操作（拷贝是 memcpy、QBUF 是 ioctl），保证 4 缓冲池不耗尽
- **处理线程**：CPU 密集任务（YUYV→JPEG 编码、HTTP/RTSP 帧分发、录像写入），与采集解耦
- **RTSP 线程 / 控制线程**：各自独立的阻塞事件循环（epoll），互不阻塞
- **MJPEG 服务器**：常驻 accept 线程监听 HTTP 连接，每接入一个客户端派生一个 detached handler 线程持续推送帧（动态线程，数量 = HTTP 客户端数）
- **关键设计**：采集与推流/录像分离，避免推流阻塞（TCP 拥塞、磁盘 IO）导致缓冲区耗尽掉帧

### 3.3 采集线程完整工作详解（每帧循环 9 件事）

承接 3.2，采集线程**不只是拷贝**——它是 **V4L2 缓冲队列的驱动者**。每帧循环做 9 件事（`main.cpp:873-965`）：

```cpp
while (g_state.running) {
    // ① 暂停检查与握手（885-892）
    if (g_state.paused) {
        g_state.pausedAck = true;
        g_state.pauseCv.notify_one();
        g_state.pauseCv.wait(lk, [] { return !g_state.paused.load(); });
        continue;
    }
    // ② 读取用户目标帧率（895）
    throttleFps = g_state.targetFps.load();
    // ③ V4L2 取帧：dqbuf（897-900）
    if (capture->getFrame(&fb, 1000) < 0) { ... continue; }
    // ④ 帧率节流：太快则丢帧（902-914）
    if (throttleFps > 0 && elapsedMs < 1000/throttleFps) {
        capture->putFrame(&fb); continue;   // 归还缓冲，跳过本帧
    }
    // ⑤ 诊断统计：每 100 帧打印实际帧间隔（916-940）
    // ⑥ 拷贝帧到共享区（942-950）
    { std::lock_guard<std::mutex> lock(g_state.mtx);
      g_state.frameData.assign(fb.data, fb.data + fb.length); ... }
    // ⑦ PERF 插桩（951-953）
    g_perf.copyBytes += fb.length; g_perf.frames++;
    // ⑧ V4L2 归还缓冲：qbuf（956）
    capture->putFrame(&fb);
    // ⑨ 通知处理线程（958-963）
    { std::lock_guard<std::mutex> lock(g_state.procMtx); g_state.frameReady = true; }
    g_state.procCv.notify_one();
}
```

**核心职责：V4L2 缓冲队列管理**（拷贝只是"把 mmap 帧搬运到共享区"的一环）：

| 调用 | V4L2 动作 | 作用 |
|------|----------|------|
| `getFrame`（`capture.cpp:454`） | **`dqbuf`** | 从驱动取出已填好数据的缓冲，返回 mmap 指针（零拷贝） |
| `putFrame`（`capture.cpp:486`） | **`qbuf`** | 把用完的缓冲还回驱动队列，让摄像头 DMA 可写下一帧 |

**设计哲学**：采集线程刻意保持轻量——只做"取帧 → 快拷 → 快还 → 通知"（微秒级），**推流/编码/录像/解码全在别的线程**（`main.cpp:970` 注释"与采集解耦避免阻塞取帧"）。若采集线程被慢操作阻塞，4 个 mmap 缓冲耗尽 → 硬件无法投递新帧 → **采集饿死丢帧**。

> 一句话：**采集线程 = "V4L2 缓冲队列的管家"**——dqbuf/qbuf 循环保证硬件不断流，拷贝只是途中搬运，帧率节流/暂停握手/诊断统计是它比"纯拷贝"多做的实事。

#### 3.3.1 暂停检查与握手（运行时重配置的安全停靠）

这是 ① 的深化。**作用**：确保采集线程停止使用 V4L2 mmap 缓冲后，主线程才敢 `stopCapture()` 重配摄像头——否则就是 use-after-free。

**触发场景**：运行时重配置（`main.cpp` 三个回调）——`onResolutionChanged`（:1202）切分辨率、`onFormatChanged`（:1231）切格式、`onFramerateChanged`（:610）切帧率。它们都要调 `capture->stopCapture()`（STREAMOFF + **munmap**），而采集线程此刻可能正卡在 `getFrame()` 里**持有 mmap 缓冲**——若直接 munmap，采集线程访问已释放内存 → 崩溃；且 `VIDIOC_S_PARM` 在 STREAMON 期间返回 **EBUSY**（:609 注释），必须先停流。

**完整握手时序**（两段代码对照）：

```cpp
// ── GUI/控制线程（发起方，main.cpp:1206-1213）──────────────
g_state.paused = true;                              // ① 置暂停标志
{
    std::unique_lock<std::mutex> lk(g_state.pauseMtx);
    g_state.pauseCv.wait_until(lk, now + 1100ms,
        [] { return g_state.pausedAck.load(); });   // ④ 等"已确认"（≤1.1s）
}
capture->stopCapture();   setFormat(...);   startCapture();   // ⑤ 安全重配
g_state.paused = false;   g_state.pauseCv.notify_one();        // ⑥ 恢复

// ── 采集线程（main.cpp:885-892）─────────────────────────────
if (g_state.paused) {                               // ② 检查到暂停
    g_state.pausedAck = true;                       // ③ 确认"我已停靠"
    g_state.pauseCv.notify_one();                   //    唤醒主线程
    std::unique_lock<std::mutex> lk(g_state.pauseMtx);
    g_state.pauseCv.wait(lk, [] { return !g_state.paused.load(); });  // ⑦ 睡到恢复
    continue;
}
g_state.pausedAck = false;                          // 重新开始前清除确认
```

```
GUI 线程                          采集线程
① paused = true ──────────────►
④ wait_until(pausedAck)         ② 检查到 paused
    │                           ③ pausedAck = true + notify
    ◄────────────────────────────
⑤ stopCapture/setFormat/start   ⑦ wait(!paused)  ← 不再碰任何缓冲
⑥ paused=false + notify ───────► 被唤醒 → 继续取帧
```

**三个关键设计点**：
1. **`pausedAck`（确认信号）保证确定性**：主线程不是"盲目 sleep 等采集线程停"，而是**收到确认才操作**——语义是"我已经在安全位置了"。`paused`/`pausedAck` 都是 `std::atomic`（:64-67），跨线程无锁读写。
2. **`wait_until` + 1.1s 超时防死锁**：`getFrame` 内部 `dqbuf` 有 **1000ms 超时**（:897），采集线程最坏 1s 内必回循环头检查到 `paused`；主线程等 1.1s（留余量）必能收到确认，采集线程异常卡死也不会永久阻塞主线程（注释："getFrame 有 1s 超时，最多等 1.1s"，:1207）。
3. **条件变量 + 谓词防唤醒丢失**：`wait_until(lk, 谓词)` 先查 `pausedAck` 再睡——若采集线程在 `wait` 前就置好 `pausedAck`，谓词已为 true 直接返回不睡。

| 作用 | 防的是什么 |
|------|-----------|
| 防止 use-after-free | 采集线程还在用 mmap 缓冲时 `munmap` → 崩溃 |
| 避免 EBUSY | STREAMON 期间 `VIDIOC_S_PARM`/`setFormat` 被驱动拒绝 |
| 确定性时序 | `pausedAck` 确认代替盲目 sleep，杜绝"主线程以为停了其实没停"的竞态 |
| 防死锁 | 1.1s 超时兜底，任何卡死都不会永久阻塞 |

> 一句话：**这是"生产者停靠协议"**——重配置前先让采集线程"停到安全点并确认"，做完再唤醒。三段式（置标志 → 确认 → 等恢复）是嵌入式"重配硬件前停生产者"的标准模式。

### 3.4 线程同步方案

- 共享帧数据由 `std::mutex` 保护：采集线程深拷贝到 `g_state.frameData` 后立即归还 mmap 缓冲，消费者各自短锁拷贝出私有副本，杜绝悬垂指针（遗留的 `setFrame()` 深拷贝接口已废弃无调用点，显示链路走 `setFrameShared` + 帧池共享）
- MJPEG 推流用**条件变量广播**：新帧到达唤醒所有等待的 HTTP 客户端
- 每个网络连接独立接收缓冲区，天然解决 TCP 粘包/拆包

#### 3.4.1 notify_all()：条件变量广播详解

`notify_all()` 是 C++11 标准库 `<condition_variable>` 中 `std::condition_variable` 的成员函数——**唤醒所有正在等待该条件变量的线程**，是"生产者-消费者"同步模型里的**广播信号**。

**作用**：与 `wait()` 配对。消费者 `wait(lk, 谓词)` 挂起（睡眠不占 CPU），生产者写完共享数据后 `notify_all()` 广播"数据好了"，被唤醒的线程重新抢锁、重查谓词、谓词为 true 才继续。**唤醒 ≠ 立即执行**——只是"可调度"，真正准入靠谓词。

| | `notify_one()` | `notify_all()` |
|---|---|---|
| 唤醒数量 | 1 个 | 所有等待线程 |
| 适用场景 | 单消费者 | 多消费者广播 |
| 本项目例子 | `procCv.notify_one()`（采集→唯一处理线程） | `m_frameCV.notify_all()`（处理→N 个 HTTP 客户端线程） |

**本项目三处使用**：
1. **MJPEG 广播（1→N，`mjpeg_server.cpp:301`）**：`updateFrame`（处理线程）存好最新帧后 `m_frameCV.notify_all()`，N 个 HTTP 客户端线程各自 `wait_for`（:456）检查谓词 `m_frameIndex != lastIndex`，有新帧才醒、取帧发送——这是"一次采集广播给所有观众"的实现；
2. **单消费者通知（`main.cpp:963`）**：采集线程 `procCv.notify_one()` 通知唯一的处理线程；
3. **退出广播（`main.cpp:1423`）**：程序退出时 `procCv.notify_all()` 唤醒处理线程使其退出循环。

**底层机制**：条件变量内部维护**等待队列**；`wait()` 原子地"释放锁 + 挂起 + 入队"；`notify_all()` 把队列中所有线程移出标记可调度，随后重新竞争锁、重查谓词。Linux 上由 **futex** 系统调用实现，等待期间不占 CPU。

**三个必须知道的坑**：
1. **必须配谓词**：`wait(lk, 谓词)` 先查谓词再睡，**防止丢失唤醒**（notify 发生在 wait 之前时，谓词已为 true 直接不睡）；
2. **虚假唤醒**：没有 notify 也可能被系统唤醒——谓词是"重新确认条件"的兜底，**绝不能裸 `wait()` 不配谓词**；
3. **notify 不必持锁**：`updateFrame` 就是先释放 `m_frameMtx` 再 `notify_all`（`mjpeg_server.cpp:253-301`），避免被唤醒线程立刻阻塞在锁上。

> 一句话：**`notify_all()` = "条件变量广播"**——`wait()` 睡、`notify_all()` 叫醒所有，配合谓词保证"数据好了才知道、醒了还要再确认"。MJPEG 的 N 客户端推送正是靠它实现的 1→N 广播。

### 3.5 帧池零拷贝（显示链路）

为消除显示链路反复深拷贝，新增 header-only 的 `FramePool`（`include/common/frame_pool.h`），核心思想 **"数据共享，而非数据搬移"**：

- **`FrameSlot`**：帧槽（`std::vector` 数据 + `std::atomic` 引用计数 + seq 序号）
- **`FramePool`（RGB 显示池，容量 2）**：
  - `acquire()` 借空闲槽（refs 0→1），池满返回 nullptr → **丢帧而非阻塞**
  - `publish()` 原子发布为"当前"（release 语义 + release fence）
  - `share()` 取当前槽共享引用（refs+1，acquire 语义）
  - `release()` 归还引用（refs-1，归 0 后可复用）
- **核心不变量**：`acquire` 只借空闲槽 → 生产者写 `refs==1` 的槽、消费者读已发布的 `m_current` 槽，天然读写分离（双缓冲），无锁并发
- **生命周期安全**：`SlotGuard`（RAII 句柄）全覆盖，所有 `share()` 结果强制归还，防漏 release / use-after-free

```cpp
// displayTimer 帧池路径（GUI 主线程，完全单驱动）
FrameSlot* slot = g_rgbPool->acquire();        // 借槽，无空闲则丢帧
decodeJPEGtoRGB(raw, ..., slot->data);          // 解码直接写入池槽（消除二次拷贝）
g_rgbPool->publish(slot);                       // 原子发布
gui.setFrameShared(g_rgbPool->share());         // GUI 持有引用，QImage 浅引用上屏
gui.requestRefresh();                           // 发布后立即上屏（唯一驱动入口，无相位延迟）
```

【口头陈述】

> "架构上最重要的决策是把**采集和推流分离到不同线程**。V4L2 的缓冲区池只有 4 个，如果采集线程被慢速客户端或磁盘 IO 阻塞，缓冲区耗尽就会掉帧。所以采集线程只做 DQBUF、拷贝、QBUF 三个 O(1) 操作，CPU 密集的编码推流、RTSP、控制协议各自独立线程，慢操作绝不出现在采集路径上。
>
> 后来我又做了一次更深层的优化——**帧池零拷贝**。我发现一帧从摄像头到屏幕要被深拷贝 5 次，在单核上纯 memcpy 就吃掉大量带宽。我用一个基于引用计数的帧池，让显示链路从'搬数据'变成'共享数据'：生产者写槽、消费者通过共享引用读同一份数据、谁最后用完谁释放。实测把每帧拷贝从 10MB/s 压到 0.5MB/s。这个优化让我真正理解了单核嵌入式的瓶颈分析——不是盲目加线程，而是先量化到底哪里在烧 CPU。"

## 4. 核心技术选型

| 技术点 | 选型 | 原因与取舍 |
|--------|------|-----------|
| 视频采集 | V4L2 + mmap | Linux 标准视频框架；mmap 零拷贝避免用户态拷贝 |
| 采集格式 | MJPEG / YUYV 双模式 | MJPEG：摄像头硬件直出，零 CPU 编码；YUYV：原始帧，软件编码，兼容性更好 |
| 颜色转换 | 定点运算（BT.601） | 无浮点单元开销；后续升级 NEON 向量化 |
| JPEG 编解码 | libjpeg-turbo | NEON 加速、嵌入式友好；自定义静默错误处理器抑制坏帧崩溃 |
| HTTP 流 | multipart/x-mixed-replace | 浏览器原生支持，无需插件 |
| RTSP | 自实现 RFC 2326 + RFC 2435 | 深度可控、理解协议本质；避免 Live555 的 GPL 许可与移植成本（详见难点 §12.4） |
| 网络模型 | epoll 边缘触发 + 非阻塞 I/O | 单线程管理数千连接，适配嵌入式资源 |
| 控制协议 | 自定义 TCP 二进制协议 | 紧凑、可控；CRC-16/MODBUS + 魔数 + 长度三重校验 |
| GUI | Qt5 Widgets + linuxfb | 成熟的跨平台框架；linuxfb 免 X Server，直接写 framebuffer |
| 录像封装 | AVI（RIFF + MJPEG） | 无编码器依赖、结构简单、易于自实现索引 |
| 构建 | CMake + ARM 交叉编译 | 跨平台；toolchain + sysroot 隔离系统库版本差异 |
| 系统集成 | systemd | 崩溃自重启、开机自启、安全加固、journald 日志 |

【口头陈述】

> "选型上我坚持一个原则：**能用标准框架就不重复造轮子，但协议栈要自己写**。比如视频采集用内核标准的 V4L2，GUI 用 Qt5，JPEG 用 libjpeg-turbo——这些是稳定可靠的基础设施。而 RTSP 协议栈和 TCP 控制协议我选择从零实现，因为对嵌入式求职来说，理解协议的信令流程、RTP 分片、CRC 校验这些底层细节，恰恰是面试官最看重的深度。"

## 5. 功能模块划分

### 5.1 视频采集模块（camera/capture）

- V4L2 标准流程：`open → querycap → s_fmt → reqbufs → querybuf → mmap → qbuf → streamon → dqbuf`
- mmap 零拷贝 + **4 缓冲区轮转池**
- 运行时动态切换格式 / 分辨率 / 帧率
- 摄像头参数控制：亮度 / 对比度 / 白平衡 / 曝光 / 帧率（V4L2 Control + VIDIOC_S_PARM）

### 5.2 图像处理模块（camera/processor）

- YUYV → RGB24 定点转换（BT.601，无查表）
- libjpeg-turbo 编解码（编码用于 YUYV 模式推流；解码用于缩略图/相册/显示路径）
- `decodeJPEGtoRGB`：显示链路 JPEG→RGB24 解码，结果直接写入帧池槽（自定义静默错误处理器，坏帧不崩溃）
- NEON SIMD 加速（详见 §8.3）

### 5.3 流媒体模块（network/）

- **MJPEG-over-HTTP**：`/`（实时流）、`/snapshot`（单帧快照）、`/status`（JSON 状态）
- **RTSP/RTP**：DESCRIBE/SETUP/PLAY/TEARDOWN 全信令，RTP 分片 + RFC 2435 JPEG 载荷，epoll 驱动多会话
- **TCP 控制协议**：命令帧格式 `[魔数2][版本1][命令1][长度2][负载N][CRC2]`，支持拍照/录像/分辨率/格式/状态查询/心跳

### 5.4 存储管理模块（storage/manager）

- 拍照：JPEG 文件，按日期分目录
- 录像：AVI（RIFF + MJPEG + idx1 索引块），按帧率控制
- 磁盘空间管理：按修改时间自动清理，达到阈值（如 keep_mb=100）删除旧文件
- 存储路径可在 tmpfs（/data，快但易失）与 eMMC（/home/debian/smartcam，持久）间切换

### 5.5 显示与交互模块（display/）

- 主界面：实时预览、拍照、录像、状态栏（Cap FPS 采集 / Disp FPS 显示 / 分辨率 / 存储空间 / 客户端数）
- 设置面板：亮度/对比度/白平衡/曝光/帧率，V4L2 联动 + 互锁逻辑；Format 下拉框与实际采集格式双向同步（`setCurrentFormat`）
- 相册：缩略图网格、全屏查看、多选删除、存储空间状态栏（<5% 红色警告）
- 视频播放器：轻量 AVI 解码器，QTimer 帧率控制，进度条 seek，不依赖 ffmpeg

### 5.6 系统集成与公共模块（common/）

- INI 配置：三级优先级（命令行 > 配置文件 > 硬编码默认值）
- 日志：分级 + syslog 集成 + journald 统一收集
- 环形缓冲区、共享类型定义
- 帧池零拷贝 `frame_pool.h`（FrameSlot / FramePool / SlotGuard，header-only）

【口头陈述】

> "整个系统按职责拆成了 6 个模块，模块之间只通过清晰的接口协作。比如采集模块不关心推流，它只负责把帧通过回调分发出去；推流模块不关心存储，它只订阅帧数据。这种解耦让每个模块都能独立测试、独立演进——比如相册多选删除、曝光控制这些新功能，都是在这个架构上增量加进去的，没有影响其他模块。"

## 6. 关键业务流程

### 6.1 视频流链路（核心）

```
摄像头 → V4L2 DQBUF → 帧数据
              │
              ├─ MJPEG 模式：JPEG 直出 ──→ HTTP 流 / RTSP 流 / 存储（零编码零解码）
              │
              ├─ YUYV 模式：软编码 JPEG ──→ 同上（一次编码，多处复用）
              │
              └─ 本地显示：解码/转换 → 写入 RGB 帧池槽 → publish → setFrameShared → requestRefresh 浅引用上屏（零拷贝，单驱动）
```

一次采集，三路消费（UI 预览 / HTTP / RTSP），编码结果共享避免重复计算；本地显示链路走帧池零拷贝（见 §3.5）。

### 6.2 RTSP 会话流程

```
客户端            SmartCam RTSP 服务器
  │  DESCRIBE rtsp://IP:8554/stream      │
  ├─────────────────────────────────────►│  解析 URL，返回 SDP（含媒体描述）
  │  ←─────────── 200 + SDP ────────────┤
  │  SETUP (transport=RTP/AVP)           │
  ├─────────────────────────────────────►│  分配 RTP/RTCP 端口，建立会话
  │  ←─────────── 200 + 端口信息 ────────┤
  │  PLAY                                │
  ├─────────────────────────────────────►│  开始向客户端推送 RTP 分片
  │  ←─────────── 200 ──────────────────┤
  │  持续接收 RTP 数据流…                 │
  │  TEARDOWN                           │
  ├─────────────────────────────────────►│  释放会话资源
  │  ←─────────── 200 ──────────────────┤
```

### 6.3 TCP 控制协议帧处理

```
接收缓冲 → 找魔数(0xEB 0x90) → 校验版本 → 读长度 → 凑齐完整帧 → CRC 校验
                                                        ├─ 通过 → 分发命令 → 回响应帧
                                                        └─ 失败 → 丢弃（清缓冲 + 记日志）
```

- 命令表驱动分发（map<cmd, handler>），扩展新命令只需注册回调
- 心跳超时（默认 30s）自动断开失联客户端

### 6.4 拍照 / 录像流程

- **拍照**：GUI 或 TCP 命令触发 → 取最新一帧 JPEG → 按 `日期/IMG_xxx.jpg` 落盘 → 相册自动刷新
- **录像**：启动时创建 AVI 文件（写入 RIFF 头 + avih + idx1 占位）→ 逐帧写入 MJPEG chunk → 停止时回填 size 字段与 idx1 索引

### 6.5 相册浏览流程

`listPhotos → 懒加载可见区域缩略图（scale_denom 快速解码）→ 网格显示 → 点击全屏/播放 → 删除（单删/多选批量）→ 空间状态栏实时刷新`

【口头陈述】

> "最有代表性的一条链路是**一帧数据的旅程**：摄像头 DMA 把 MJPEG 帧写进 mmap 缓冲区，采集线程 DQBUF 后拷贝出来立刻归还缓冲区，然后这一帧同时被三路消费——Qt 主线程渲染到屏幕、HTTP 模块通过 multipart 推给浏览器、RTSP 模块切成 RTP 分片发给播放器。在 YUYV 模式下则先过一次软编码，编码结果三路共享，保证 CPU 只花一份钱。"

## 7. 数据流与状态管理方案

### 7.1 全局状态管理

- 共享状态集中在全局结构 `g_state`，由 `std::mutex` 保护
- 读-改-写一律持锁；UI 刷新通过 Qt 信号槽跨线程安全投递
- 帧数据深拷贝策略：采集线程深拷贝到 `g_state` 后立即归还 mmap，消费方各持私有副本，杜绝指针悬垂（遗留 `setFrame()` 接口已废弃，显示链路走 `setFrameShared`）
- **帧池共享**：显示链路 RGB 帧用 `FramePool` 引用计数共享（`share`/`release`），取代部分深拷贝——核心不变量"acquire 只借空闲槽"，靠 `std::atomic` + 内存序（publish=release / share=acquire）保证无锁安全

### 7.2 数据流分层

| 层级 | 数据 | 流向 | 同步机制 |
|------|------|------|---------|
| 采集层 | mmap 帧缓冲 | 内核 DMA → 用户态 | DQBUF/QBUF 协议 |
| 分发层 | 帧拷贝 | 采集线程 → UI/HTTP/RTSP | mutex + 条件变量 |
| 存储层 | JPEG/AVI 文件 | 内存 → 磁盘 | 独立写线程/加锁 |
| 控制层 | 命令帧 | 客户端 ↔ 服务器 | 每连接独立接收缓冲 |
| 显示层 | RGB 帧槽 | GUI 解码 → 上屏 | 帧池引用计数（无锁双缓冲） |

### 7.3 配置状态

- 三级优先级：**命令行 > 配置文件 > 硬编码默认值**
- 配置变更（如存储路径、分辨率）通过回调即时生效，无需重启
- 用户级配置（`~/.config/smartcam/`）覆盖系统级（`/etc/smartcam/`）

【口头陈述】

> "状态管理上我做了两层设计：**运行时的帧数据**用互斥锁 + 深拷贝，保证并发安全；**配置数据**用三级优先级解析，让命令行、配置文件、默认值各司其职。另外所有跨线程的 UI 更新都走 Qt 信号槽，避免了手动锁导致的死锁风险。"

## 8. 性能优化策略

### 8.1 零拷贝与零编码路径

- **V4L2 mmap**：内核 DMA 缓冲区直接映射用户态，省去 read 系统调用的两次拷贝
- **MJPEG 硬件直出**：摄像头直接输出 JPEG，推流零 CPU 编码开销（这是 iMX6ULL 无 VPU 场景下的最优解）

### 8.2 帧池零拷贝（显示链路）

- 用 `FramePool`（双缓冲 + 引用计数）消除显示链路 2 次 RGB24 深拷贝（`setFrame` 的 assign + `QImage.copy()`）
- 解码结果直接写入池槽，GUI 用 **QImage 浅引用**上屏（不 `.copy()`），上屏前只剩一次物理必需的 QPixmap 拷贝
- **实测**：显示链路拷贝从 **10.0 MB/s → 0.5 MB/s（-95%）**，池预分配 2 槽仅 +0.3MB 常驻内存
- 核心价值：为 720p 升级预留带宽（640x480 的 0.92MB RGB 拷贝已占 CPU，720p 是 2.76MB，零拷贝使其不再受搬运约束）

### 8.3 算法层优化

- **定点运算**：YUYV→RGB 用整数运算实现 BT.601，避免浮点开销
- **NEON SIMD**：颜色转换向量化，16 像素/轮，**约 8× 加速**（详见 docs/07）
- **缩略图快速解码**：libjpeg `scale_denom` 直接缩到目标尺寸再解码，节省 4~16× 内存与 CPU

### 8.4 内存控制

- 固定帧缓冲池（4 个 mmap 缓冲），无运行时大块分配
- RGB 显示池预分配固定 2 槽（~1.84MB），稳态零 realloc，消除每帧 vector 分配抖动
- 视频播放器流式读取：每次只从磁盘读一帧，不预载全部帧
- 相册懒加载：只加载可见区域的缩略图

### 8.5 网络层优化

- epoll 边缘触发：一次事件循环读完所有就绪数据，避免多次系统调用
- 帧数据单次编码多路复用：HTTP/RTSP/存储共享同一份 JPEG

### 8.6 实测性能数据（iMX6ULL Cortex-A7 @ 792MHz）

| 操作 | 耗时/开销 | 备注 |
|------|----------|------|
| MJPEG 硬件输出 | < 1ms | 摄像头直出 |
| YUYV → RGB24 | ~5ms | 定点运算 |
| libjpeg-turbo 编码（640x480） | ~25ms | NEON 加速 |
| **JPEG 显示解码（640x480）** | **~15-25ms** | 曾误判为瓶颈；实测硬件输出 10fps 才是帧率上限（见 §12.9） |
| JPEG 缩略图解码（→170px） | ~15ms | scale 1/2 |
| 推流运行内存 | ~8MB | 帧缓冲 + JPEG 拷贝 |
| 相册峰值内存 | ~2.5MB | 6 张缩略图 + 1 张全尺寸 |
| **显示链路拷贝** | **0.5 MB/s** | 帧池零拷贝后（原 10.0 MB/s，-95%） |

【口头陈述】

> "性能优化我遵循**先架构后算法**的顺序。架构层面先解决了两件大事：一是 mmap 零拷贝，二是 MJPEG 零编码路径——这两项直接决定了 792MHz 单核能不能跑 30fps。算法层面再用定点运算和 NEON 把软件路径压下来。最终推流状态整个进程只有 8MB 内存，这个数字在面试时可以直接作为工程能力的量化证明。
>
> 后来我用性能插桩做了量化分析，发现一个很有价值的结论：**帧池零拷贝把拷贝量降了 95%，但帧率纹丝不动**。我又逐步排除了解码、渲染，甚至把渲染全去掉后 CPU 降到 67%、帧率还是 10fps——**这证明瓶颈在硬件供给端**。最终用 `v4l2-ctl` 直测确认是摄像头实际输出 10fps（能力列表声称 30fps 但实际不是）。这让我学会了一件事：嵌入式性能排查不能靠直觉，必须先插桩量化、逐层排除，**最终用工具直测硬件供给能力**。"

## 9. 安全性措施

### 9.1 systemd 服务加固

| 措施 | 配置 | 作用 |
|------|------|------|
| 文件系统只读 | `ProtectSystem=full` | 防止 /usr /boot /etc 被篡改 |
| 家目录隔离 | `ProtectHome=yes` | 阻断访问 /root /home |
| 私有临时目录 | `PrivateTmp=yes` | 独立 /tmp，防进程间干扰 |
| 内核参数保护 | `ProtectKernelTunables/Modules=yes` | 禁止修改内核参数/加载模块 |
| 地址族限制 | `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX AF_NETLINK` | 只放行网络与本地 socket |
| 显式可写路径 | `ReadWritePaths=/data /tmp` | 最小权限原则 |

### 9.2 协议层安全

- **CRC-16/MODBUS 校验**：所有控制帧校验，防传输损坏
- **魔数 + 版本 + 长度三重确认**：防粘包/错位/垃圾数据
- **心跳超时断开**（30s）：自动清理失联客户端，防连接耗尽
- **边界防护**：最大帧长限制（8 + 4096），防恶意超大负载

### 9.3 健壮性

- **静默错误处理器**：libjpeg 自定义 error handler，坏帧只告警不崩溃
- **systemd 崩溃自重启**：`Restart=on-failure` + 3s 延迟
- **优雅停止**：SIGTERM → 10s 超时 → SIGKILL，录像文件正确收尾

【口头陈述】

> "嵌入式设备的安全不能只靠网络层，我做了两层。第一层是 systemd 的沙箱化：文件系统只读、家目录隔离、限制地址族，让即使进程被攻破也拿不到太多东西。第二层是协议本身：CRC 校验防止数据损坏，魔数加长度防止恶意构造，心跳超时防连接耗尽——对一个开放端口给远程控制的设备来说，这些是底线。"

## 12. 遇到的难点与解决方案

### 12.1 难点一：内存严重受限（512MB，可用 <200MB）

**问题**：i.MX6ULL 可用内存不足 200MB，而 `git push` 的 delta 压缩会触发 OOM killer，大内存操作会拖垮系统。

**解决**：
- 推流内存控制到 ~8MB（帧缓冲池 + 零拷贝）
- git 推送关闭 delta 压缩（`pack.window=0`）+ 10MB 分包，绕开单文件限制与内存峰值
- 缩略图 scale_denom、流式读取等内存策略（见 §8.3）

**面试延伸**：内存受限下如何做设计取舍（见面试题 4.1）。

### 12.2 难点二：触摸屏不响应

**问题**：linuxfb 下触摸无反应。

**解决**：排查定位为**设备权限不足**——`/dev/input/event*` 默认 660 (root:input)，普通用户无权读取。修复：`chmod 666`（临时）或 `usermod -aG input`（永久）。

**面试延伸**：linuxfb 输入子系统、权限模型（见面试题 2.5）。

### 12.3 难点三：重启后照片丢失

**问题**：照片写入 `/data`，但 `/data` 是 tmpfs，断电/重启即失。

**解决**：Settings 面板增加 **Store 下拉框**，可在 tmpfs（快）与 eMMC（持久）之间切换，切换即时生效并持久化到用户级配置，重启自动恢复。

**面试延伸**：tmpfs vs 持久化存储、配置持久化设计（见面试题 2.5）。

### 12.4 难点四：RTSP 协议栈从零自实现（vs 使用 Live555）

**问题**：主流方案是 Live555 库，但带来 GPL 许可、体积大、移植成本、学习不透彻等问题。

**解决**：自实现 RFC 2326 信令（DESCRIBE/SETUP/PLAY/TEARDOWN）+ RTP 分片 + RFC 2435 JPEG 载荷 + epoll 驱动多会话。深度可控，代码量可控，且彻底理解协议本质。

**面试延伸**：为什么不用 Live555？是面试高频追问（面试题 2.4 / 6.2）。

### 12.5 难点五：帧率调节触发 `VIDIOC_S_PARM` 返回 EBUSY

**问题**：STREAMON 期间直接改帧率失败。

**解决**：先暂停采集 → 停流 → `VIDIOC_S_PARM` → 重启流 → 恢复采集的完整序列；软件节流（`g_state.targetFps`）兜底。曝光方面实测发现"强制手动曝光保帧率"的方案在该固件上会让摄像头输出黑帧（v4l2-ctl 实证），最终改为"只查询不写入"，保留自动曝光（自动曝光在暗光下拉长曝光确实会把 30fps → ~10fps，但这是硬件行为，应用层如实记录帧率，不再强行干预）。

**面试延伸**：V4L2 状态机、曝光与帧率耦合（面试题 5.1、10-settings-panel）。

### 12.6 难点六：AVI 容器与播放器兼容问题

**问题**：自写 AVI 文件被外部播放器拒绝 / 自写播放器解析失败。

**解决**：按 RIFF 规范修复：movi LIST size 字段回填、chunk 对齐 padding（奇数偏移补字节）、idx1 `dwChunkLength` 规范修正；播放器按 idx1 索引 seek 精确定位每一帧。

**面试延伸**：RIFF/AVI 容器结构、二进制格式解析（debug-summary）。

### 12.7 难点七：Docker sysroot 交叉编译

**问题**：云端开发无法直连开发板，宿主系统库版本与板子不匹配。

**解决**：打包板子根文件系统 → 分包经 GitHub 中转 → Docker（Debian Buster = glibc 2.28 / Qt 5.11.3，与开发板一致）+ 宿主 x86_64 Qt 工具（moc/rcc/uic）+ 交叉编译器内编译，ARM 库全部来自板子 sysroot，杜绝版本不匹配（见 §11.1）。

**面试延伸**：交叉编译原理、sysroot、工具链（面试题 5.2）。

### 12.8 难点八：libjpeg 坏帧崩溃

**问题**：USB 摄像头偶发坏帧，默认 error handler 直接 `exit()`，导致进程崩溃。

**解决**：自定义静默错误处理器，坏帧仅告警、不终止进程。

**面试延伸**：第三方库错误处理、嵌入式健壮性设计。

### 12.9 难点九：帧率瓶颈的完整排查——最终定位摄像头硬件 10fps（重要经验）

**问题**：CPU 已 99% 打满、帧率仅 10fps（目标 30fps），起初怀疑是反复深拷贝导致。

**排查与解决**（完整过程见 `docs/debug-summary.md` #27）：
1. **先做量化**：加 `[PERF]` 性能插桩，实测显示链路拷贝 10.0 MB/s，判断拷贝是最大优化项；
2. **做帧池零拷贝**：把拷贝从 10.0 → 0.5 MB/s（-95%）。但实测**帧率纹丝不动、CPU 仍 99%**；
3. **逐步排除应用层**：插桩显示解码 15.6ms、渲染 9ms、处理线程已跳过——**所有应用层任务都很小**；`top -H` 显示主线程烧 97%；`perf` 定位到 `QColorProfile::fromSRgb`（linuxfb 渲染颜色管理，占 ~48% CPU）；
4. **试过独立解码线程（已回退）**：曾把 MJPEG→RGB 解码移出 GUI 线程，实测**更卡**。原因：i.MX6ULL 是**单核**，线程无法并行，解码线程仍占同一个核，反而多引入 RGB 深拷贝 + 线程切换开销；
5. **决定性实验**：去掉渲染后 CPU 降到 67%（有 33% 空闲），但**帧率仍 10fps**——**CPU 有空闲却提不上帧率 → 瓶颈在供给端（硬件）**；
6. **最终根因（v4l2-ctl 直测铁证）**：**摄像头硬件实际输出 10fps**（尽管 `--list-formats-ext` 声称支持 30fps，能力列表 ≠ 实际输出）。**改任何应用代码都无法突破硬件帧率上限**。

**核心结论**：
- **单核嵌入式性能排查顺序**：先确认硬件/驱动供给能力（`v4l2-ctl` 直测），再优化应用层；
- **判断瓶颈方法**：CPU 有空闲但帧率提不上去 → 瓶颈在供给端（硬件），改应用代码无效；
- **低分辨率显示解码**（显示解码到 320x240 `scale_denom=2`，~25ms→~8ms）能省 CPU，但**无法突破硬件帧率上限**——它是在"换支持 30fps 摄像头后 CPU 成为瓶颈"时才需要做。

**面试延伸**：单核嵌入式性能瓶颈分析方法、能力列表 vs 实际输出的区别、`v4l2-ctl` 直测的重要性、多线程 vs 少计算的取舍。

【口头陈述】

> "这个项目里我最想讲的三个难点：一是**内存受限下的设计**——把推流内存压到 8MB，甚至 git 推送都要关掉压缩来避免 OOM；二是**RTSP 协议栈从零实现**——这让我真正理解了信令流程和 RTP 分片的本质，而不是停留在会调用库的层面；三是**一系列真实硬件问题**——触摸权限、tmpfs 丢数据、AVI 格式不规范，这些问题教科书不会讲，只有真机调试才能遇到，也最能体现工程经验。
>
> 特别想提一下**单核性能优化**这段：我一开始直觉以为是拷贝太多，做了帧池零拷贝把拷贝降了 95%，结果帧率没变；又以为是解码瓶颈，但把渲染全去掉、CPU 降到 67% 后帧率还是 10fps——**这说明瓶颈不在应用层**。最后用 `v4l2-ctl` 直测，确认是摄像头硬件实际输出 10fps（虽然能力列表写着支持 30fps）。这个从'直觉优化'到'逐层排除、最终工具直测硬件'的过程，是我在嵌入式性能排查上最大的收获。"
